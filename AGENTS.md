# AGENTS.md — Component Comparison Tool

This file describes the project for AI agents and automated workflows.

## What This Project Does

Compares UI components across multiple brand websites to identify overlap, naming differences, and visual/functional equivalents. Currently covers two Dutch insurance brands: **FBTO** and **Centraal Beheer (CB)**.

Input: Sitecore CMS analysis reports per brand (HTML with embedded screenshots + JSON component manifests).  
Output: A Next.js web app at `src/` showing which components exist per brand, how often they're used, which components across brands are likely the same thing under different names, and a manual review workflow for confirming or rejecting similarity matches.

## Data Shape

### `data/{brand}-report/extracted-data.json`
```jsonc
{
  "extractedAt": "ISO date",
  "totalPages": 1267,
  "totalUniqueComponents": 97,
  "components": {
    "Component Name": {
      "name": "Component Name",
      "count": 49,           // total occurrences across all pages
      "pages": [{ "url": "https://...", "filename": "slug" }]
    }
  }
}
```

### `data/{brand}-report/component-selectors.json`
```jsonc
{
  "components": {
    "Component Name": {
      "selector": ".css-selector",   // null if not mapped
      "description": ""
    }
  }
}
```

### `data/similarity.json`
```jsonc
{
  "generatedAt": "ISO date",
  "totalPairs": 392,
  "pairs": [
    {
      "brandA": "fbto", "componentA": "Accordeon block",
      "brandB": "cb",   "componentB": "Content accordion v1",
      "score": 0.58,
      "signals": { "name": 0.2, "visual": 0.594, "structural": 0.677 }
    }
  ]
}
```

### `data/manual-review.json`
```jsonc
{
  "reviews": {
    "fbto::Accordeon block::cb::Content accordion v1": "confirmed",
    "fbto::Banner::cb::Hero banner": "rejected"
  }
}
```
Keys are generated by `buildPairKey(pair)` in `src/lib/data.ts`. Values are `"confirmed"` | `"rejected"`. Key is absent (or removed) when status is `"unreviewed"`.

## Similarity Signal Weights

| Signal | Weight | Method |
|--------|--------|--------|
| Visual | 50% | Perceptual hash (pHash) on 64×64 grayscale screenshots |
| Name | 30% | Jaccard on normalized tokens + Dutch→English synonyms |
| Structural | 20% | Tag-sequence Jaccard from DOM component sections |

Pairs with combined score ≥ 0.4 are included. Pairs ≥ 0.7 are "Likely same", ≥ 0.5 "Possibly same".

## Manual Review System

The detail page groups similar components into three sections (re-sorted live on every decision):

| Group | Color | Position |
|-------|-------|----------|
| ✓ Confirmed same | Green | Top |
| ? Needs review | Yellow | Middle (default) |
| ✕ Not the same | Red | Bottom |

- `ReviewButtons` — two toggle buttons; clicking the active one undoes the decision  
- `ReviewBadge` — shown in the overview table when a pair has been reviewed  
- `SimilarComponentsSection` — fetches `/api/review` on mount, re-fetches after each save  
- `/api/review` GET/POST — reads/writes `data/manual-review.json` directly on the server

## Adding a Brand

1. Create `data/{id}-report/` with `extracted-data.json`, `component-selectors.json`, `report.html`
2. Add entry to `BRANDS` in `src/lib/brands.ts`
3. Run `npm run analyze` (repo root)
4. Run `cd src && npm run build` or `npm run dev`

The UI adapts automatically — no other code changes needed.

## Running the App

```bash
# Repo root — install dependencies
npm install

# Run similarity analysis (required before first use, or after adding a brand)
npm run analyze

# Start web app
cd src
npm install   # first time only
npm run dev   # → http://localhost:3000
```

## Constraints & Gotchas

- `getScreenshotUrl()` returns `null` for components without a screenshot — always null-check in UI
- `buildPairKey(pair)` in `src/lib/data.ts` generates canonical review keys — use this, do not construct keys manually
- `report.html` files are large (10–14 MB) — parsed only during `npm run analyze`, not at runtime
- The Next.js app's `process.cwd()` is `src/` — data files are accessed via `path.join(process.cwd(), '..', 'data', ...)`
- Screenshots are copied to `src/public/screenshots/{brand}/` by the analyze script — commit these or re-run analyze after cloning
- Scripts use ESM modules — run via `tsx`, not `ts-node`
- Do not add client-side event handlers (`onClick`, `onError`, etc.) to Server Components (Next.js App Router) — wrap in a `'use client'` component instead
- `/api/review` is a dynamic route (server-rendered on demand) — all other pages are SSG
